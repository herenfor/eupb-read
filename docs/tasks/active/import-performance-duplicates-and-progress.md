# 任务：导入性能、重复识别与阅读进度可靠性

- 状态：已同步，待 Windows 安装包确认
- 创建日期：2026-08-17
- 最后更新：2026-08-17
- 对应 Bug：B-020、B-021

## 目标

1. 修复书架阅读进度保存失效，保证快速翻页、首次打开与返回书架时不会被旧写入覆盖。
2. Windows 发布版保存 EPUB/封面不再把二进制展开为 JSON 数字数组；批量拖放保持单本有界内存。
3. 内容完全相同的 EPUB 在写盘前识别并跳过，既有文件、封面、首次添加时间与阅读进度均不改变。
4. 批量导入期间不逐本刷新背景书架，全部完成后只合并一次 UI 状态。
5. 单本重复显示红色“此书已经被导入过了哦”；批量结果最多列出两个截断后的重复书名，更多时追加“等书”。

## 非目标

- 不把内容发生变化的 EPUB 自动替换旧书或迁移阅读进度；内容不同默认作为新书。
- 不实现多写入者并发或跨进程书架同步。
- 不修改 EPUB 解析、消毒和分页兼容规则。
- 不引入相邻章节预加载、搜索、书签或高亮功能。

## 当前现象与证据

- Windows 发布版通过 `Array.from(Uint8Array)` 传输正文和封面；15.21 MiB 测试书在本地同类转换中产生约 140 MiB JS 堆，JSON 参数约 54.25 MiB。
- 原生批量拖放使用 `Promise.all`，先把所有 EPUB 读进 WebView，再逐本处理。
- 重复上传当前仍完整解析并覆盖 EPUB/封面，只在保存条目时保留旧进度；重复项被计入导入成功。
- 导入循环每成功一本立即 `setShelfEntries`，触发重复排序、渲染和封面加载。
- 阅读进度每次 ready 状态都直接发起异步 `updateProgress`；返回书架不等待落盘，错误被静默吞掉；首次打开的 `markOpened` 与进度更新可能并发写同一个索引临时文件。

## 已确认根因

- 导入 CPU 主因：Tauri 保存路径把 EPUB/封面转成 JSON 数字数组再反序列化为 `Vec<u8>`。
- 批量内存放大：拖放路径一次性读取全部文件，导入状态又逐本写回 React。
- 重复导入语义错误：现有 ID 只基于 identifier/文件名/大小，且保存前没有跳过，实际文件仍被覆盖。
- 进度失效来自写入生命周期没有顺序与最终提交保证：多个异步更新独立执行、失败静默、返回书架不等待，首次 `markOpened` 还可能用陈旧整条记录覆盖内存进度；Rust 索引变更也没有统一写入互斥。

## 必须保持的行为

- 旧版 `shelf.json` 和 IndexedDB 条目必须兼容读取，现有书籍 ID 与目录不得迁移。
- 进度继续包含章节、页码、百分比、内容锚点、最近阅读时间和新书状态。
- 精确重复必须完全跳过写盘；懒补内容指纹只能增加指纹字段。
- Tauri 与浏览器存储保持等价语义；目标路径仍只由 Rust 后端生成。
- 书架索引继续采用临时文件替换，书籍正文也应使用同目录临时文件后提交。

## 实际修改

- 新增 `src/ui/importBooks.ts`：SHA-256、0.1.5 同大小候选懒补指纹、重复提示格式和一次性条目合并。
- 新增 `src/ui/progressWriter.ts`：同书待写值合并、跨书串行、flush 失败重试。
- `App` 导入入口统一为逐本 `ImportSource`；原生拖放不再 `Promise.all`，重复在解析/保存前跳过，整批结束后只更新一次书架。
- 单本重复使用红色指定文案；批量统计真实新增/重复/失败，重复书名最多两本、单名最多 14 个 Unicode 字符，更多追加“等书”。
- 新导入用内容 SHA-256 作为 ID/`contentHash`；旧条目不迁移 ID，首次遇到同大小候选时读取原文件补录指纹。
- Tauri 文件输入改为 raw body；原生路径直接复制；正文和封面先暂存，提交时复检重复并只写一次索引。
- 所有 Rust 索引修改经单一 `Mutex`；进度先乐观合并内存，再由单通道后台写入，返回书架、隐藏和关闭窗口时 flush。
- 主窗口关闭事件先阻止默认关闭，flush 成功后通过显式 `core:window:allow-destroy` 权限销毁窗口；写入失败时保留窗口并提示错误。
- `markOpened` 完成后只合并 `isNew:false`，不再用整条旧返回值替换更新后的进度。

- [x] 同一 EPUB 改名后仍识别为重复；同名但内容不同可作为新书导入。
- [x] 单本和批量重复提示满足用户指定文案、数量、截断和“等书”规则。

- [x] 旧版无内容指纹的书架能够读取并按需补录，不更改进度。
